# ADR-006: Idempotent ingestion

**Status:** Accepted · 2026-10-05

## Context
Mobile networks drop responses; SDKs retry. Double-counted revenue is the fastest way to lose trust.

## Decision
- Every event carries an `event_id` (generated by the SDK at call time, or the business id such as an order id). `(environment_id, event_id)` is unique; duplicates are counted, not stored.
- Requests may carry `Idempotency-Key`; the response is stored in `event_batches` and replayed for the same key.
- Events without an id get a server id and a warning.
- The SDK derives its idempotency key from the batch's events so retries reuse it.

## Consequences
- At-least-once delivery from clients becomes effectively exactly-once storage per environment.
- Customers must not reuse event ids for different events; documented in [events](../events.md).
