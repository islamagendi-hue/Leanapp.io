# ADR-006: Idempotent ingestion

**Status:** Accepted · 2026-10-05

## Context
Mobile networks drop responses; SDKs retry. Double-counted revenue is the fastest way to lose trust.

## Decision
- Every event carries an `event_id` (generated by the SDK at call time, or the business id such as an order id). `(environment_id, event_id)` is unique; duplicates are counted, not stored.
- Requests may carry `Idempotency-Key`; the response is stored in `event_batches` with `payload_hash` (sha256 of the request's ordered event ids, or an event's canonical JSON when it has no id) and replayed for the same key and the same events. The same key with different events gets `409 idempotency_key_reused` and nothing is stored, so a response is never replayed for events that were not stored. Hashing ids rather than the raw body keeps retries idempotent although SDKs re-serialize them (new `sent_at`, possibly another key order). Rows from before migration 0028 have no hash and replay as before.
- Events without an id get a server id and a warning.
- The SDK derives its idempotency key from every event id in the batch (`<size>:<FNV-1a of the ids>:<first id>`) so retries of the same batch reuse it and a batch whose events changed between a lost response and the retry (consent, TTL, queue cap) gets a new one. On `409` the SDK keeps the events and resends them without a key.

## Consequences
- At-least-once delivery from clients becomes effectively exactly-once storage per environment.
- Customers must not reuse event ids for different events; documented in [events](../events.md).
